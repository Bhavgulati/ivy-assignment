# Frontend

Vite + React + TypeScript. Three runtime dependencies: react, react-dom,
react-router-dom. No UI kit and no data-fetching library — the parts that would
have justified one (paging, token refresh, caching) are the parts this
assignment is actually about, so they are written out where they can be read.

```
npm install
npm run dev        # http://localhost:5173
npm run build      # tsc -b && vite build -> dist/
```

Sign in with `demo1@ivy.homes`, `demo2@ivy.homes` or `demo3@ivy.homes` and the
password issued with the API key.

## Deploying

`vercel.json` and `public/_redirects` both rewrite unknown paths to
`index.html`. Without one of those a listing URL pasted into a fresh tab 404s,
because the router runs in the browser and the host has no such file.

## Where the numbers come from

`public/manifest.json` is generated by `analysis/build_submission.py` in the
same run that writes `submission.json`. It carries the unit-correction rules and
the lists of records flagged impossible, not genuine, duplicated, or stated in
the wrong unit.

The app reads that file rather than reimplementing the rules in TypeScript. The
reason is drift: two copies of a rule eventually disagree, and then the screen
and the submission tell a reviewer different things. With one generator, a rule
change moves both or neither.

`npm run build` does not regenerate the manifest. If a rule changes, run
`python3 build_submission.py` from `analysis/` first.

## Things worth knowing before reading the code

- **`src/api/client.ts`** holds the session and refreshes it. The access token
  lives 900 seconds, not the documented 86400, and `POST /auth/refresh` exists
  despite the reference saying there is no refresh flow. One refresh runs at a
  time behind a shared promise; six simultaneous 401s would otherwise start six
  refreshes, five of which would present an already-rotated token and log the
  user out mid-session.
- **Paging is by `offset`.** `page` is accepted and ignored, `limit` is clamped
  to 50 whatever is requested, and `total` under-reports by about 8.6%, so
  `has_more` is the only stop condition used anywhere.
- **Filters.** Only `locality`, `bhk`, `property_type`, `furnishing`,
  `min_price` and `max_price` were verified to actually filter server side.
  Those are sent. `is_live`, `is_verified`, `project_id`, `website`,
  `posted_by`, `min_area`, `max_area`, `q` and `search` are accepted and
  silently ignored, so they are never sent — requesting a filter the server
  drops would show the user an unfiltered list and call it filtered. The live
  and flagged toggles are applied in the browser for the same reason.
- **Saved listings are local.** `/v1/favourites` returns 404 on all three
  documented methods, so there is no server to save to. The key is scoped by
  account email, which satisfies the brief's requirement that the list survive a
  reload and a re-login. It does not follow the user to another device; fixing
  that needs the endpoint the documentation claims already exists.
- **Insights computes everything.** `/v1/analytics/summary` is a 404, so that
  screen pulls the whole collection — 82 requests at the real page size — and
  aggregates in the browser, reporting progress as it goes.

## Known limitations

- The API key ships in the client bundle, because the API only accepts it as a
  request header from the browser. It is published in `submission.json` anyway,
  so nothing is leaked here that was not already public, but the production
  shape is a small server holding the key and the session and handing the
  browser a cookie.
- The session token is in `localStorage`, so any script on this origin can read
  it. The fix is an httpOnly cookie, which needs that same server.
- `useCollection` caches a whole collection in memory for the session. At 4,100
  listings that is fine; it would not be at 400,000.
- No tests. With more time the first three would be the unit-correction
  functions, the offset pager against a fake envelope, and the single-flight
  refresh under concurrent 401s.
