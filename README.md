# Ivy Homes assignment — Chennai

A frontend over the property API, and an audit of everywhere its documentation
disagrees with it.

- **App:** https://ivy-assignment-sepia.vercel.app
- **Answers and findings:** [`submission.json`](./submission.json)
- **Key:** `IVY26-C947D32E59D7` · city Chennai · assigned locality Guindy

    analysis/   the harness and the probes. Python, standard library only.
    app/        the frontend. Vite + React + TypeScript.
    submission.json   generated by analysis/build_submission.py, never hand-edited.

## Running it

    # the audit
    cd analysis
    cp .env.example .env          # add the key and password
    python3 ivy.py discover --write     # ~120 requests: probe the API surface
    python3 ivy.py fetch --details 25   # ~480 requests: full crawl, twice, plus a
                                        # third traversal in a different order
    python3 ivy.py report               # distributions over the snapshot
    python3 probe2.py                   # then probe3, probe4, probe5 in order
    python3 build_submission.py         # writes submission.json and the app manifest

    # the app
    cd ../app
    npm install
    npm run dev

Total API usage for a full reproduction is about 600 requests against a limit of
1200 per minute, and the client throttles itself to roughly 600 per minute.
`analysis/out/requests.jsonl` logs every one of them, including the failures,
with the key substituted out and the password never written.

The snapshot itself is gitignored. It is a full dump of one city and this
repository is public, so publishing it would hand it to anyone else working on
the same city. Anyone with a key can regenerate it in two minutes.

## How I decided what to distrust

The documentation announces that it is unreliable, which means it cannot be used
as a test oracle — and neither can the data, since the brief says a seller can
write anything. So there were only two usable sources of truth: the API's own
behaviour, and internal consistency.

**First, the cheap half.** One script that asks the API what it does and records
the raw answer: which of key and token is required and where each goes, what the
envelope really looks like, whether `page` or `offset` moves the window, what the
limit ceiling actually is, which documented paths exist, and which query
parameters are accepted and then ignored. About 120 requests, and it found
seventeen discrepancies in the first hour. The very first request answered
itself — the 401 body says in plain English that the key goes in a header, not
the query parameter the reference documents.

**Then the expensive half, which is the actual assignment.** Nothing above
required a hypothesis. Duplicates, unit errors and fraud do not appear in any
single response, so I pulled the whole dataset once and stopped treating it as an
API. Four techniques did the work:

1. **Digit histograms instead of means.** A money or area column that is 90%
   seven-digit values and 10% five-digit values is not a column with outliers, it
   is two units sharing a column. A mean hides that completely. This is what
   surfaced the square-metre areas, the month-count deposits, and the project
   prices.

2. **Looking for the gap rather than aiming at a number.** For duplicates I swept
   one matching rule across distances from 10 m to 300 m and watched the count.
   It falls to 3,117 at 100 m and then does not move at all through 300 m. The
   plateau is the answer. Earlier I had guessed at match keys and read off
   whichever landed nearest the server's `total` of 3,749 — which is circular,
   because the same analysis had already shown `total` under-reports. I threw
   that away.

3. **Measuring multipliers instead of picking tolerances.** My first answer for
   the costliest project was wrong, and it was wrong because my test allowed a
   0.5× to 2.0× band, which is wide enough that "98% of listings fall in range"
   carried no information. Replacing it with the distribution of
   `listings_max / price_max` split cleanly into two clusters at 10^7 and 10^5,
   which is what the field actually does.

4. **Counting how often a rule is already right.** For the project listing
   counts, four readings were plausible. Counting every record leaves 336 of 460
   projects wrong; counting live listings leaves 119 wrong, 341 exactly right,
   and no bias in the error. A rule that makes three quarters of the data wrong
   is more likely to be the wrong rule than a description of a broken field.

**The trap the brief warned about.** "The first rule that fits will usually fit
most of the data. Look hard at what it gets wrong." That happened three times:

- A naive impossibility check flagged 147 records with no bedrooms. Most were
  plots. Land has no bedrooms. The real corrupt set is 63 records, and what
  identified it was a count of exactly nine recurring across seven unrelated
  defects with no overlap between them.
- My first dedup key matched on `apartment_name`, which is a building, not a
  property — a building holds fifty flats. Close pairs agree on the building name
  only 48% of the time, because each portal re-types it. Matching had to become
  geometric.
- A duplicate cluster held four records near 1,261 sqft and one at 113. That one
  record was in square metres, and 333 records like it were quietly breaking both
  the area maths and their own duplicate matching.

**And `/llms.txt`.** The service advertises it from `GET /`, and it contains a
table of per-city figures that map exactly onto questions 1, 2, 3 and 10. It also
says, of itself, that it was "generated from the same changelog as the API
reference, by the same assistant, the same afternoon, and reviewed by the same
nobody." Its number for this city is 3,916 listing records. The API serves 4,100.
I used it as a hypothesis to test and not as a source, and every figure it gave
turned out to be wrong.

## What I checked that turned out to be fine

These took real time and produced nothing, which is the point of listing them.

| Hypothesis | Why I suspected it | Result |
| --- | --- | --- |
| `listing_id`s repeat | The reference asserts global uniqueness twice, which reads like overcompensation | **True as documented.** 4,100 records, 4,100 distinct ids, zero collisions |
| Offset paging skips rows over a non-unique sort key | A classic bug: two records tie on price, the server orders them differently between requests, one slides across a page boundary and is never returned | **Clean.** I crawled a third time ordered by price and diffed the id sets against the default traversal. Identical, both directions |
| Paging is unstable between runs | Would invalidate every count | **Stable.** Crawled at limit 50 and again at limit 25; same 4,100 ids |
| The detail endpoint disagrees with the list rows | Two code paths over one record often drift | **Consistent.** 25 sampled, zero differences |
| Records from another city leak through | The brief lists "records the endpoint should not have returned" as a finding type | **No.** All 4,100 are `city_id` 4 |
| Locality strings have case or whitespace variants | The reference promises lowercase, and that promise is usually broken | **Kept.** No variants. `/v1/localities` agrees |
| The 8.6% gap between `total` and reality is one excluded locality | `velachery` matched the gap exactly in rentals (133) and projects (38) | **Coincidence.** It does not match in listings, and the shortfall holds proportionally under every filter, including `property_type=plot` at 126 against 138 served |
| `total` is a de-duplicated count | It would have explained the gap in all three collections at once, and it is the kind of thing that gets mislabelled | **No.** Dedup lands on 3,117, not 3,749. I could have forced a match by loosening the key and did not |
| Rental rent is in the wrong unit | The brief calls out "correct prices" for rentals specifically | **Correct as documented.** ₹8,000–93,200 a month. The unit problem is in `deposit`, not `price` |
| `/v2/listings`, `/v2/insights/summary` etc. exist | `/llms.txt` advertises four of them in detail | **They 404**, and the error says so: "there is no /v2; llms.txt announced it early." Not reported as findings — they are absent from the reference *and* from the service, so they are neither a missing nor an undocumented endpoint |
| Fraud shows up as volume, or as `is_verified` false | The obvious shape | **Both wrong, and backwards.** The five largest portfolios in the city are ordinary agents. The fake set is *100% verified* while the market runs at 60% |

## What I left out of the findings on purpose

Precision is scored as heavily as recall, so these are here rather than in
`submission.json`:

- `/robots.txt`, `/ads.txt`, `/humans.txt`, `/.well-known/ai-plugin.json` — live,
  and absent from the reference, so technically undocumented endpoints. They are
  web conventions rather than API surface and I did not think they belonged.
- `/register` — a registration page, not an endpoint.
- `/health` carrying an explicit `+05:30` offset — the brief's own example says
  this one is not a discrepancy.
- 422 bodies putting an array of validation objects in `detail` where the
  reference promises a string. Real, small, and I was not confident enough it was
  on the list.

## The findings, in one paragraph

The key goes in a header. Paging is by offset and `page` is silently ignored.
`limit` clamps to 50, not 200. `total` under-reports by 8.6%, so the documented
way of fetching everything loses 351 listings. Tokens last 15 minutes, not 24
hours, and the refresh flow the reference says does not exist does. Favourites
and analytics are documented and return 404. Project prices are in Indian display
units — below 10 means crores, 10 and above means lakhs — which is why `price_min`
exceeds `price_max` for 357 of 460 projects if you believe the documentation. 333
listings state area in square metres; missing that puts rupees-per-square-foot
63.7% too high. 63 records are physically impossible, 110 exist to farm
enquiries, and 983 are the same property listed again on another portal.
Twenty-eight findings in `submission.json`, each with the evidence that
reproduced it.

## With another two days

- **Tests.** There are none, which is the largest gap. The first three would be
  the unit-correction functions against known inputs, the offset pager against a
  fake envelope that lies about `total`, and the single-flight refresh under
  concurrent 401s. I wrote a mock of the API early on to test the harness before
  pointing it at the real service; that mock should have grown into the test
  fixture and did not.
- **A real threshold for the fraud set.** The seven contacts are separated by a
  visible gap on three signals at once, which I trust, but the cut is still a
  number I chose. I would rather have a calibration: label the obvious ones, fit
  on those, and report where precision starts to fall.
- **The duplicate rule's failure modes.** 100 m and 2% on carpet area are
  plateau-derived, not principled. I would want to see the pairs the rule
  narrowly rejects.
- **A small server for the app.** It would hold the API key and the session and
  hand the browser an httpOnly cookie, which is the honest fix for both of the
  security limitations in `app/README.md`. I did not build it because CORS is
  open and the key is published in this repository anyway, so it would have been
  structure without a reason.
- **Why `total` is short by exactly 8.6% in every collection and every filter.**
  I can demonstrate it and I cannot explain it, and that bothers me more than
  anything else on this list.
